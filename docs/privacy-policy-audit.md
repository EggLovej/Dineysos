# Privacy policy evidence review

Reviewed on 25 October 2026. The German and English policy files were revised together.

## Outcome and limits

The original policy was a template rather than an accurate inventory of this website. Confirmed technical and business facts are now described, placeholders have been removed, and unsupported assurances have been narrowed. This is an evidence review and corrected local draft, **not confirmation that every processing activity is lawful or that the notice is ready for publication without the open checks below**.

Following the owner's editorial review, the public notice was shortened: section 1 identifies the company without the additional paragraph naming its operators; section 2 provides the deletion contact and confirmation commitment without the internal workflow; section 5 summarises contact, feedback, brochures and consent in four sentences; section 7 covers event photos and their removal. Provider disclosures and links are consolidated in section 8. The technical evidence and unresolved account details remain documented here. The owner requested confirmation after deletion and removal of event photos on request; these are operational commitments to honour, not processes independently observed by this audit.

Scope: current `quick_update` checkout, active routes and API handlers, retired brochure UI, the public production site, connected Vercel project metadata, official provider documentation, and the owner's answers in this chat. The stashed contact-form/privacy implementation was not used or applied. No production forms were submitted, emails sent, customer records queried, account settings changed, or deployment performed.

## Actual processing added to the notice

- `src/pages/_app.tsx:15`: Web Analytics and Speed Insights mount on all pages. Production DOM contains `/_vercel/insights/script.js` and `/_vercel/speed-insights/script.js`. No `identify`, `group`, custom analytics event, or ad-pixel integration was found in application code. Optional features in a provider's downloaded script do not prove those features are used here.

No name/email field is required by that form. Free text can still identify someone; it is not accurate to call every response anonymous.
- `src/components/sections/Gallery.tsx:96`: enlarged photos use raw Sanity CDN URLs. Preview images pass through Next image optimisation; the lightbox can contact Sanity directly.

- `src/components/layout/Layout.tsx:6`: Cormorant is configured with `next/font`.

### Existing brochure service and historical records

`src/legacy/README.md` confirms the brochure UI was retired; the API remains active. The notice deliberately distinguishes it from a currently visible homepage form.

`src/pages/api/requestBrochure.ts` processes an email address, language, update preference, sent status and sent timestamp in the `emails` table. Resend delivers a brochure and sends an administrative notification that does not include the requester's address in its message body. The endpoint also verifies a Cloudflare token and passes the client's IP address. A re-enabled widget would process browser signals as described by [Cloudflare](https://www.cloudflare.com/turnstile-privacy-policy/).

The owner confirmed Hostpoint for business email, no newsletters sent so far, possible future updates only for opted-in people, and manual deletion requests via email/administrator.

**Consent bug fixed:** the API previously treated an omitted preference as `true`, and the retired UI started checked. The API now requires the boolean value `true`; the retired UI starts unchecked and remains retired. This does not establish valid consent for historical rows. Requesting a brochure still requires storing its delivery address even if newsletter updates are declined.

## Remaining decisions and checks

1. **Existing photos:** confirm publication permissions or another valid justification for the actual images with Clint and Marina. Recognisable people retain image/privacy rights in group photos too; being a group is not a blanket exemption. The [FDPIC's photo guidance](https://www.edoeb.admin.ch/en/photos-and-privacy) explains the distinctions. The revised notice offers a contact/removal route and does not invent existing consent.
2. **Historical mailing list:** verify affirmative consent records before sending a first newsletter. An old `wantsUpdates=true` value may originate from the preselected/default behaviour and is not sufficient proof on its own. No historical records were modified or read during this review.
3. **Retention:** choose actual retention periods or criteria for enquiries, feedback, brochure/update records, photos and backups. Manual deletion is the current fact, not evidence that indefinite retention is lawful. The owner also needs a process for provider copies and mailbox records, not just the application database.
4. **GDPR/electronic-communications requirements:** decide the applicable audience/jurisdictions and the appropriate basis/consent controls for analytics and photos. Cookie-less analytics is not automatically outside privacy law. Current scripts run on page load; no new consent banner or opt-out was introduced or claimed.
5. **Processing locations and contracts:** confirm the Supabase project region, provider/subprocessor destinations, applicable DPAs and transfer mechanisms for the actual accounts. The [FDPIC's notice guidance](https://www.edoeb.admin.ch/en/duty-to-provide-information) calls for recipient and destination information. Provider headquarters alone do not fulfil that verification.
6. **Email tracking:** verify Resend domain-level open/click tracking and retention before claiming it is off. [Resend documents tracking as a configurable domain feature](https://resend.com/blog/introducing-custom-tracking-domain); a vendor default is not proof of this account's settings.
7. **Technical access/security:** review live database permissions and backups separately. This review establishes data paths, not that every database access control or organisational measure is adequate.
8. **Company details:** corroborate the supplied UID/register details in the official registry if independent confirmation is required; VAT status was not established by this review.

### Access limits encountered

- Vercel project/deployment metadata was accessible; environment-variable metadata returned HTTP 403. The mapped CLI was not installed. No credential decryption or account change was attempted.
- Local configuration identifies Supabase project `kpldrdzbbqjwncelxkbg`. The connected Supabase account only exposed a different project; accessing the relevant project was denied. No region from that other project was reused and no database contents were read.

- The browser interface exposed DOM/scripts, not a complete cookie/storage/network inspector. A public HTTPS response with no `Set-Cookie` and a source scan support the narrow application-cookie wording, not a universal claim that no infrastructure cookie can ever appear.

### Separate behaviour issue found, outside this change

The generic `/feedback` page sends `{rating, comment}`, whereas the API only accepts `type: "sip-solve"`. It also displays success without checking `response.ok`.
